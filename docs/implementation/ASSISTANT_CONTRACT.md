# Assistant and floating helper contract

Contracted 2026-10-04. This slice is a user-operated route assistant, not autonomous app control or screen guidance. No screen is captured, no accessibility content is read, and no message/call/payment is dispatched.

- `AssistantActivity` is non-exported and owns the general-assistant microphone. Text routing starts only from its explicit Ask control; its microphone starts only from its explicit Speak control while resumed and after microphone permission and a speech-provider disclosure. Opening Home or the overlay never starts listening. Background, Stop, cancellation and destruction invalidate callbacks and disconnect optional inference. The existing QR screen separately retains explicit foreground amount dictation: recognized text is parsed locally only, guarded by the QR screen, and cannot call Maa's backend. The phone speech provider may still process that voice remotely; local amount parsing is not a claim of offline recognition.
- Deterministic Hindi/English routes open Home, family selection, Apps, alarms, family help and the owned WhatsApp-family workflow. Recipient selection and final communication stay in `CommunicationActivity` and the receiving app. Ambiguous requests remain editable. A QR/payment classification does not execute a transaction or silently interpret an amount.
- Optional `/intent` classification requires a configured HTTPS endpoint, explicit `ai_cloud_consent` bound to that endpoint, and a new explicit request. Only the submitted text is sent. No screenshots, photos, contact directory or passive speech are included. Speech-provider processing is a separate disclosure; offline speech is not promised.
- Backend replies accept only `call`, `media`, `qr`, `help`, `home`, `unsupported`. HTTP redirects are refused; input, response size and connection/read times are bounded. Unknown keys/types/actions fail closed. Cancellation/background prevents a late route even if already-transmitted bytes cannot be recalled. Tokens and transcripts are not logged.
- Floating helper starts from the existing explicit user enablement. A collapsed movable control expands to Ask Maa, Family and Home plus collapse/stop. Drag position and intended enablement persist; actual attachment is reported separately. Loss of overlay permission, app stop or close removes the window. No claim of guaranteed restart or continuous overlay confinement is made.
- Service notification provides a stop action and foreground assistant entry. A desired-on preference does not prove the service is currently visible. Root must use the exposed live-state check for health. Boot restart is outside this slice; Android may stop the process.

Integration: declare `.AssistantActivity` non-exported; route the Home Ask Maa button to its explicit intent. Do not retain the old MainActivity cloud/microphone route as an alternate consent bypass. Existing overlay/foreground-service permissions and speech-service package query remain relevant. No new broad package query or screen-observation permission is required.

Use `HelpOverlayService.stop(context)` for explicit disablement so both the service and desired-on preference are cleared. `isActive(context)` checks actual window attachment and overlay permission; `isRequested(context)` reports persisted preference only. An existing `startForegroundService(Intent(context, HelpOverlayService::class.java))` records explicit enablement. Permission loss leaves desired enablement recorded but actual status false; a later permission grant requires an explicit start unless Android independently restarts the existing sticky service.

Verification: compile and focused instrumentation under the root build coordinator; manual microphone grant/deny/revoke, unavailable recognition, cancel/background during inference, changed endpoint, denied overlay, drag/clamp/rotation, service close and process death. Any unexecuted test remains unverified. Tests must not send messages, place calls or make payments.
